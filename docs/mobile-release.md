# Mobile release foundation

Loadnote v2.54 established a reproducible mobile packaging boundary. v2.63 adds an authenticated server-only online Coach boundary on top of the v2.60 consumer Profile/account experience, v2.61 program lifecycle and v2.62 gym-floor polish, but App Store / Play Store distribution, concrete provider provisioning, native redirect validation, background synchronization, and multi-instance transactional storage are still incomplete.

## Current mobile shell

- Capacitor app name: `Loadnote`
- Current development app identifier: `app.loadnote.mobile`
- Web bundle directory: `www`
- Web assets are produced by `npm run sync:www`.
- `npm run check:mobile` rebuilds `www` and verifies the package boundary, install manifest, safe-area setup, service-worker asset references and release version.

The current app identifier is suitable for development packaging. Review the final bundle/application identifiers before provisioning production App Store or Play Store records. Once production store identities and signing are established, treat those identifiers as release infrastructure rather than casually changing them.

## Package boundary

The mobile web bundle intentionally contains the consumer application shell and its browser assets. It does not copy:

- `backend/`
- `tests/`
- `.github/`
- environment files or server-side secrets

The AI provider secret remains server-side. Native packaging must not move provider secrets into the client bundle.

## Runtime surfaces

`src/product/platform-runtime.js` distinguishes:

- regular browser
- installed standalone web app
- native Capacitor shell

The result is exposed as `window.LoadnoteRuntime` and as document/body runtime markers so later mobile work can add platform-specific behavior without scattering user-agent checks across the application.

This detection does not unlock fake native features. Code should still verify that any native capability actually exists before using it.

## Safe areas

The application opts into `viewport-fit=cover` and applies safe-area insets to the installed/native app shell, toast placement, bottom navigation spacing and gym-mode controls. This is intended to prevent training controls from sitting under notches or home indicators.

## Native project generation

Native iOS/Android project folders are not generated by this release.

After the final application identifiers/signing plan are reviewed, generate native projects with the installed Capacitor CLI (iOS builds require macOS/Xcode; Android requires its SDK/toolchain):

```
npm run sync:www
npx cap add ios
npx cap add android
npx cap sync
```

Generated native projects then need physical-device validation and platform-specific review before any commercial release.

## Required checks before a mobile release

Run:

```
npm ci
npm run check
npm test
npm run check:mobile
npm run test:browser
```

Also perform the manual iPhone/Android acceptance work documented in `docs/testing.md`. Automated Chromium tests do not prove iOS WebView, Android WebView, signing, store metadata, permissions or physical-device behavior.

## Still not completed after v2.63

This release does **not** implement:

- production provider provisioning and native redirect/callback validation for the selected identity service
- multi-instance transactional account storage
- background/automatic synchronization (manual conflict-first sync exists in v2.59)
- subscription/payment infrastructure
- App Store or Play Store signing
- native push notifications
- production telemetry/crash reporting
- production store listings

Those should be introduced as separate reviewed milestones rather than implied by the existence of a Capacitor configuration.


## Gym-floor interaction layer (v2.62)

The workout logger now exposes mobile keyboard hints, a current-set/rest/Finish dock, previous-set context and explicit previous-set reuse. The dock is presentation only: the recoverable workout draft remains the source of truth and workout saving remains local.

Previous loads are read from normal workout history in storage kilograms and converted at display time. The UI never stores display pounds as internal kilograms. Use-last does not copy RPE, completion state or a hidden readiness interpretation.

The dock uses the browser visual viewport only to avoid competing with a likely on-screen keyboard. Native iOS/Android keyboard behavior still requires physical-device acceptance testing; this release does not claim Chromium viewport behavior proves App Store-quality keyboard handling.


## Secure Coach boundary (v2.63)

The mobile/browser bundle contains Coach context-building and transport code, but no AI provider key, provider base URL, selectable model, or trusted system-prompt configuration. Production online Coach requires the Loadnote account/session boundary and calls the Loadnote backend; provider credentials are configured only on the server.

The browser sends a bounded structured context rather than raw provider messages. Weight-bearing context fields remain kilograms internally and are explicitly named as kg fields before leaving the device. Provider output is parsed on the server and returned as a bounded structured Coach result. No response is automatically applied to a workout or program.

A future native release still needs concrete OIDC/native redirect provisioning and real-device sign-in testing. v2.63 does not add native bearer-token persistence.
