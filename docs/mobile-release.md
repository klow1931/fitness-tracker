# Mobile release foundation

Loadnote v2.54 establishes a reproducible mobile packaging boundary without claiming that App Store / Play Store distribution, accounts, or cloud sync are complete.

## Current mobile shell

- Capacitor app name: `Loadnote`
- Current development app identifier: `app.loadnote.mobile`
- Web bundle directory: `www`
- Web assets are produced by `npm run sync:web`.
- `npm run check:mobile` rebuilds `www` and verifies the package boundary, install manifest, safe-area setup, service-worker asset references and release version.

The current app identifier is suitable for development packaging. Review the final bundle/application identifiers before provisioning production App Store or Play Store records. Once production store identities and signing are established, treat those identifiers as release infrastructure rather than casually changing them.

## Package boundary

The mobile web bundle intentionally contains the consumer application shell and its browser assets. It does not copy:

- `backend/`
- `tests/`
- `.github/`
- environment files or server-side secrets

The AI provider secret remains server-side. Native packaging must not move provider secrets into the client bundle.

## Runtime surfaces

`src/product/platform-runtime.js` distinguishes:

- regular browser
- installed standalone web app
- native Capacitor shell

The result is exposed as `window.LoadnoteRuntime` and as document/body runtime markers so later mobile work can add platform-specific behavior without scattering user-agent checks across the application.

This detection does not unlock fake native features. Code should still verify that any native capability actually exists before using it.

## Safe areas

The application opts into `viewport-fit=cover` and applies safe-area insets to the installed/native app shell, toast placement, bottom navigation spacing and gym-mode controls. This is intended to prevent training controls from sitting under notches or home indicators.

## Native project generation

Native iOS/Android project folders are not generated by this release.

After the final application identifiers/signing plan are reviewed, the existing scripts can be used:

```
npm run add:ios
npm run add:android
npm run sync
```

Generated native projects then need physical-device validation and platform-specific review before any commercial release.

## Required checks before a mobile release

Run:

```
npm ci
npm run check
npm test
npm run check:mobile
npm run test:browser
```

Also perform the manual iPhone/Android acceptance work documented in `docs/testing.md`. Automated Chromium tests do not prove iOS WebView, Android WebView, signing, store metadata, permissions or physical-device behavior.

## Not completed in v2.54

This release does **not** implement:

- accounts or authentication
- cloud synchronization
- subscription/payment infrastructure
- App Store or Play Store signing
- native push notifications
- production telemetry/crash reporting
- production store listings

Those should be introduced as separate reviewed milestones rather than implied by the existence of a Capacitor configuration.
